Protecting the Digital Front Door

MISSION 06

“The network road is protected…

but what if the website itself has a weak door?”

🧭 Mission Connection — From Network Security to the Web

In Session 5, we followed information across a network. We learned that firewalls act like gatekeepers, IDS and IPS watch for suspicious behavior, and segmentation limits how far an attacker can move. Now imagine that the network is well protected, but a public website contains a programming mistake. A visitor can reach the website through the allowed front door, because the website is supposed to be available. The problem is that the application behind that door may trust user input too much.

This is where web security begins. A web application is a conversation between a browser, a web server, application code, databases, APIs, identity systems, and often third-party services. Every part of that conversation creates assumptions. Web security asks whether those assumptions are safe. Does the application properly authenticate users? Does it authorize every sensitive action? Does it validate input? Does it protect sessions? Does it keep secrets out of source code? Does it prevent untrusted data from becoming executable code?

Today we will learn web security through a story about a university portal. We will meet the ideas behind authentication and authorization, sessions and cookies, input validation, injection, cross-site scripting, CSRF, secure password handling, HTTPS, security headers, access control, API security, logging, and secure development. The objective is not to teach students how to attack real websites. It is to teach them how developers and defenders recognize weaknesses, design safer systems, and investigate authorized security findings.

🏫 Topic 1 — How a Web Application Works

📖 Story: The University Help Desk

Imagine a student named Arun visiting a university portal to download his attendance report. He opens a browser and types the portal address. The browser is like a student standing at the reception desk. The web server is like the receptionist who receives the request. The application is like the staff member who understands what Arun wants, and the database is like the records room containing attendance information. Arun does not walk directly into the records room; his request travels through controlled layers.

Suppose Arun clicks “My Attendance.” The browser sends an HTTP request to the server. The application receives the request, identifies Arun's session, checks whether he is allowed to view attendance, retrieves the required data, and sends a response back to the browser. A modern application may also call APIs, authentication services, caches, and cloud components. Security must therefore protect the complete chain rather than one screen.

The most important beginner lesson is that the browser is not a trusted employee. A browser is controlled by the user, and a malicious user can modify requests before sending them. Therefore, security decisions must be enforced on the server side. Hiding a button in the browser is not authorization. The server must independently verify whether the user has permission to perform an action.

🔧 Technical Deep Dive

A simplified web request contains a method such as GET or POST, a URL, headers, and possibly a body. The server returns a status code, headers, and a response body. HTTPS adds TLS protection to the HTTP communication. Application security sits above this transport layer and deals with identity, input, business rules, session state, data access, and output handling.

A common architecture is browser → web server/reverse proxy → application → database. Security controls can exist at each layer. A reverse proxy may enforce TLS and rate limits. The application performs authentication and authorization. The database enforces appropriate permissions and safely handles queries. Logs from all layers can be correlated during investigation.

Web security therefore follows a layered approach similar to network defense in Session 5. A firewall may control reachability, but application code must still enforce business authorization. TLS can protect traffic in transit, but it cannot fix a server-side authorization bug. Security controls must address the threat at the correct layer.

🔑 Topic 2 — Authentication vs Authorization

📖 Story: The College Library

Imagine a library with two questions. First, the librarian asks, “Who are you?” You show your identity card. That is authentication. Then the librarian asks, “Which books are you allowed to access?” That is authorization. These questions are related, but they are not the same. A student can successfully prove their identity and still not have permission to access an administrator's records.

Consider a university portal. A student logs in using an ID and password. The application verifies the credentials and creates an authenticated session. Later, the student requests a faculty-only report. If the server merely checks that the student is logged in and forgets to check the required role, the application has an authorization weakness.

This distinction is one of the most important ideas in web security. Authentication answers “Who are you?” Authorization answers “What are you allowed to do?” Secure applications perform authorization checks for sensitive operations on the server, not merely during the login screen.

🔧 Technical Deep Dive

Authentication can use passwords, MFA, certificates, passkeys, or external identity providers. After successful authentication, a session mechanism usually associates future requests with the authenticated identity. Authorization may be role-based, attribute-based, resource-based, or policy-based.

A secure authorization decision should consider the requested resource and action. For example: “Can user U perform action A on object O?” This object-level check matters because two students may have the same role but should only access their own records. This is why access-control testing should include horizontal access scenarios, not only “student versus administrator.”

The safest mental model is never trust the client to decide authorization. The browser can display menus, but the server must enforce the final rule. Every sensitive endpoint should have a deliberate authorization policy.

🍪 Topic 3 — Sessions, Cookies and Tokens

📖 Story: The Temporary Visitor Pass

Imagine a campus visitor receives a temporary pass after checking in. The visitor does not have to show their identity card at every classroom door, because the pass tells security that the visitor has already completed the check-in process. A web session works in a similar way. After login, the server needs a mechanism to recognize subsequent requests as belonging to the authenticated user.

Browsers commonly store cookies that are automatically sent with requests to matching websites. A session cookie can act like a reference to server-side session state. If an attacker obtains a valid session identifier, the attacker may be able to impersonate the user for as long as that session remains valid. This is why session protection is a major part of web security.

Developers should treat session identifiers as sensitive. They should use secure transmission, appropriate cookie attributes, expiration, session rotation when appropriate, and logout/invalidation controls. The browser is a powerful client, but the server must control the authoritative security state.

🔧 Technical Deep Dive

Important cookie attributes include Secure, which helps ensure transmission over HTTPS, and HttpOnly, which prevents ordinary client-side scripts from reading the cookie. SameSite controls when cookies are sent in cross-site contexts and can reduce certain cross-site request risks. Exact behavior depends on browser and application design.

Session fixation is a conceptual risk in which an attacker attempts to cause a victim to use a session identifier known to the attacker. Regenerating the session identifier after authentication is one important defense. Session expiration and server-side invalidation reduce the useful lifetime of compromised credentials.

Token-based architectures can use formats such as JSON Web Tokens, but “using tokens” does not automatically make an application secure. Token storage, lifetime, audience, issuer validation, signing-key management, revocation strategy, and authorization logic still matter.

🧹 Topic 4 — Input Validation and Injection

📖 Story: The Restaurant Order Slip

Imagine a restaurant where customers write orders on paper. The kitchen expects a normal list such as “two dosas and one juice.” Now imagine someone writes instructions intended for the kitchen staff rather than food items. If the restaurant blindly treats every sentence as a trusted command, the process becomes dangerous. Software faces a similar problem when it takes untrusted input and mixes it directly into commands or queries.

Web applications accept input from usernames, search boxes, URLs, forms, API requests, uploaded files, and many other sources. Input is not automatically safe because it came from a browser. A malicious user can construct a request that the normal interface would never generate. Secure development therefore validates input according to the expected type and uses safe APIs that separate data from commands.

Injection is a broad class of vulnerabilities in which untrusted data changes the meaning of an interpreter's command. SQL injection is one famous example, but the concept extends to command interpreters, template engines, LDAP queries, and other technologies. The defensive lesson is to avoid constructing commands by string concatenation when a parameterized or structured interface exists.

🔧 Technical Deep Dive

For database access, parameterized queries/prepared statements allow the database driver to treat supplied values as data rather than executable query structure. This is stronger than attempting to remove a few “bad characters.” Validation remains useful, but it should complement—not replace—safe query construction.

Input validation can use allowlists where practical. If a field is supposed to be a positive integer, parse it as an integer and reject invalid representations. If a field is supposed to be one of five known categories, accept only those categories. Validation should be based on the application's business requirements rather than a fragile blacklist.

Output encoding is also important because the correct defense depends on the context where data will appear. Data inserted into HTML, JavaScript, URLs, or other interpreters may require different handling. Security is therefore about maintaining the boundary between data and code.

🧪 Topic 5 — Cross-Site Scripting (XSS)

📖 Story: The Notice Board

Imagine a campus notice board where students can post messages. The board is designed to display ordinary text. One day, someone posts a message that contains instructions intended to be executed by the board's display system rather than read as text. If the system fails to distinguish content from executable instructions, every visitor who views the message may be affected.

Cross-site scripting, commonly called XSS, occurs when an application causes untrusted data to be interpreted as executable script in a user's browser. The browser is doing what browsers are designed to do: execute scripts delivered by a page. The security failure is that attacker-controlled data crossed a boundary and became executable content in the wrong context.

XSS can appear in comments, search results, profile fields, error messages, or other places where user-controlled data is rendered. The impact depends on the application's architecture and browser protections, but it can include unauthorized actions performed through a victim's browser, manipulation of page content, or access to data available to client-side code.

🔧 Technical Deep Dive

Common categories include stored XSS, where malicious content is persisted and later displayed; reflected XSS, where input is immediately reflected into a response; and DOM-based XSS, where client-side JavaScript creates the unsafe interpretation in the browser.

Defenses include context-appropriate output encoding, safe DOM APIs, careful handling of HTML, Content Security Policy where appropriate, and avoiding unsafe string-to-code mechanisms. Developers should not assume that sanitizing a string once makes it safe for every output context.

The beginner rule is simple: untrusted data should remain data. If an application intentionally supports rich HTML, it needs a carefully designed sanitizer and a clear security model rather than blindly accepting markup.

🔄 Topic 6 — CSRF

📖 Story: The Forged Request Form

Imagine a student has already signed into a university office. Their identity is established. A stranger then hands them a form that secretly asks the office to change an important account setting. If the office accepts the request merely because the student has an active session, the stranger has found a weakness in the process.

Cross-Site Request Forgery, or CSRF, is a class of attack where a victim's browser is induced to send an unwanted request to a site where the victim is already authenticated. The browser may automatically include relevant credentials such as cookies. The application therefore needs a way to distinguish a legitimate action initiated by its own interface from an unexpected cross-site request.

CSRF is mainly about the trust relationship between a browser and a server. It is not the same as XSS. XSS executes attacker-controlled script in the trusted origin; CSRF abuses the browser's ability to send authenticated requests. Modern browser cookie controls can reduce risk, but applications should still use appropriate defenses for state-changing operations.

🔧 Technical Deep Dive

A common defense is an unpredictable anti-CSRF token associated with the user's session and included in state-changing requests. The server verifies the token before accepting the operation. SameSite cookie settings can provide additional protection, but application design should not depend on one control in every environment.

State-changing actions should generally use appropriate HTTP methods and should not be implemented as simple cross-site-friendly GET links. Sensitive actions may require re-authentication or step-up authentication. The precise defense should match the application's threat model.

The important engineering principle is to protect the intent behind sensitive actions, not merely the user's login state.

🔐 Topic 7 — Secure Password Handling

📖 Story: The Locker Room

Imagine a college keeps student locker combinations in a notebook. If the notebook contains every combination in plain text and someone steals it, every locker is immediately exposed. A safer design avoids storing the original secret in a directly reusable form. Web applications follow a similar principle for passwords: passwords should not be stored as plain text.

When a user creates a password, the application should use a password-specific hashing/key-derivation function with a unique salt. During login, the supplied password is processed again and compared with the stored password verifier. The application does not need to recover the original password. This design reduces the damage caused by a database leak, although weak passwords can still be guessed offline.

Password security is therefore connected to Session 4's cryptography lesson. A general-purpose fast hash is not a good password-storage mechanism by itself. Password storage should use an intentionally expensive password KDF such as Argon2id, scrypt, bcrypt, or PBKDF2 according to current organizational guidance and platform support.

🔧 Technical Deep Dive

A password verifier can be conceptualized as V = KDF(password, salt, cost parameters). The salt makes identical passwords produce different stored values and prevents attackers from efficiently reusing precomputed tables across accounts. Cost parameters make large-scale guessing more expensive.

Applications should also implement secure account-recovery processes, rate limiting, MFA where appropriate, and monitoring for suspicious authentication patterns. Password rules alone are not enough. A very complicated password can still be phished, reused elsewhere, or exposed through malware.

Students should remember: password storage is a specialized security problem. Encryption and password hashing solve different problems. A system should not need to decrypt a stored password because the original password should never have been stored in reversible form.

🌐 Topic 8 — HTTPS and TLS

📖 Story: The Sealed Courier Van

Imagine a courier carrying a confidential university document. You want to know three things: nobody nearby can read it, nobody secretly changes it, and you are communicating with the intended organization. HTTPS uses TLS to provide cryptographic protection for web communication and helps establish the server's identity through certificates.

When a browser connects to an HTTPS site, the TLS protocol negotiates cryptographic parameters and establishes protected communication. The server presents a certificate containing identity information and a public key. The browser validates the certificate chain according to its trust rules. Modern TLS then establishes keys used to protect the session.

The important connection to Session 4 is that asymmetric cryptography and certificates help establish trust and perform key establishment, while efficient symmetric cryptography protects the actual session data. This combination gives web communication both strong security properties and practical performance.

🔧 Technical Deep Dive

TLS provides confidentiality and integrity for data in transit when correctly configured. Certificate validation helps prevent an attacker from simply presenting an arbitrary certificate while impersonating the intended server. Trust anchors, certificate authorities, hostname validation, expiration, and key usage are part of the broader PKI model.

HTTPS does not make an application automatically secure. A website can use HTTPS and still contain broken access control, injection vulnerabilities, insecure session management, or flawed business logic. TLS protects the communication channel; application security protects the behavior of the application.

This distinction is essential for engineers: secure transport ≠ secure application.

🚪 Topic 9 — Broken Access Control

📖 Story: The Exam Office

Imagine an examination office where each student receives a file containing their own marks. Student A should not be able to open Student B's file simply by changing a number on a file request. If the office checks only that the visitor is logged in but never verifies which record belongs to them, the door is technically locked but the room's filing system is unsafe.

Broken access control occurs when an application fails to correctly enforce who can perform an action or access a resource. It can appear in ordinary web pages, APIs, downloadable files, administrative functions, or object identifiers. The vulnerability is particularly important because the application may appear to work correctly for normal users while failing under deliberate authorization testing.

The safe design is to treat every sensitive operation as an authorization decision. The server should identify the authenticated principal, identify the requested resource and action, evaluate the relevant policy, and only then perform the operation. Security should not depend on users guessing URLs or hiding interface elements.

🔧 Technical Deep Dive

Two useful test dimensions are vertical authorization and horizontal authorization. Vertical testing asks whether a lower-privileged user can perform a higher-privileged action. Horizontal testing asks whether one legitimate user can access another user's resources.

Object-level authorization is especially important in APIs. If an API receives an object identifier, the server must check that the current user has permission for that specific object. Merely validating the identifier format is not authorization.

Centralized authorization policies, consistent middleware, deny-by-default behavior, and automated tests can reduce errors. Security reviews should include negative tests: what should happen when the user attempts something they are not permitted to do?

🧰 Topic 10 — Secure Web Development

📖 Story: Building a Safe House

Imagine an engineer building a house. Security is not something added with a lock after the house is complete. The architect decides where doors go, the electrician designs safe wiring, the builder chooses strong materials, and inspectors check the work. Software security works similarly. Developers should consider threats during requirements, design, coding, testing, deployment, and maintenance.

A secure development lifecycle encourages teams to identify threats early, use secure coding patterns, review dependencies, test authorization, protect secrets, scan for vulnerabilities, and monitor production behavior. Fixing a security defect early is often easier than discovering it after deployment. Security should therefore become part of normal engineering rather than a final inspection.

Students should also learn that libraries and frameworks are valuable but not magical. A framework may provide secure defaults, but application developers can still misuse it. Developers remain responsible for configuration, authorization, data handling, secrets, and business logic.

🔧 Technical Deep Dive

Important practices include threat modeling, dependency management, secret management, code review, static analysis, dynamic testing, security-focused unit/integration tests, secure configuration, logging, and vulnerability remediation. Production systems should also have a process for responding to newly discovered vulnerabilities in dependencies.

Secrets such as API keys, database passwords, and signing keys should not be committed into source repositories. Applications should use appropriate secret-management mechanisms and rotate exposed credentials. Error messages should provide useful diagnostic information without unnecessarily revealing internal details to attackers.

Security testing should include both positive and negative cases. Developers should ask not only “Does the authorized user succeed?” but also “Does the unauthorized user fail safely?”

🧪 Safe Hands-On Activity — Build a Secure Student Portal

Step 1: Draw a login page, student dashboard, attendance API, and database.

Step 2: Define two roles: STUDENT and FACULTY.

Step 3: Write three authorization rules. Example: a student can view their own attendance; faculty can view assigned-class attendance; nobody can change another user's role.

Step 4: Identify three untrusted inputs and specify how each should be validated or safely handled.

Step 5: Add session protection, HTTPS, logging, and a recovery process.

Step 6: Perform only paper-based negative tests: “What if Student A requests Student B's record?” “What if the role is changed in the request?” “What if the search field contains unexpected syntax?”

🧩 Case Study — The Marks Portal

A university publishes a marks portal. Students log in successfully and see their marks. A security review discovers that the URL contains a record identifier. The application checks that the user is logged in but does not verify that the requested record belongs to that user. The reviewer reports that changing the identifier can expose another student's information.

Ask students: Is this authentication or authorization? The answer is authorization. The user has successfully authenticated, but the server has failed to enforce object-level access control. This is a powerful example because nothing is wrong with the login screen. The weakness exists in the business rule controlling which resource the authenticated user may access.

Now ask how to fix it. The server should retrieve the authenticated user's identity from trusted session state, check whether that user is authorized to access the requested record, and deny the operation otherwise. The application should also log meaningful access-control failures and add automated tests for both allowed and denied cases.

🔬 Research Connection — Turn Web Security Into Research

Web security offers many research opportunities for first-year students. A student can compare different approaches to detecting anomalous login behavior, study the effect of rate limiting on brute-force resistance, evaluate false positives in web anomaly detection, or measure how secure coding patterns reduce common vulnerability classes in a controlled educational application.

A simple research project could create a safe local web application with intentionally different defensive configurations. One version could use basic input handling, while another uses parameterized queries and validation. Students can measure the number of unsafe test cases detected or prevented. The goal is not to attack public websites; the goal is to construct an authorized experimental environment and collect measurable evidence.

Another project could examine access-control testing. Students can define users, roles, and resources, generate authorized and unauthorized requests in a local application, and measure whether the policy consistently blocks invalid combinations. This introduces students to reproducible experiments, datasets, metrics, hypotheses, and evidence-based conclusions.

🧠 ELI10 Summary — The Web Security Castle

Think of a web application as a castle. HTTPS protects the road to the castle. Authentication checks who has arrived. Authorization decides which rooms they may enter. Session management controls the visitor pass. Input validation checks what visitors bring inside. Injection defenses prevent visitors from turning ordinary objects into commands. XSS defenses stop untrusted content from becoming scripts. CSRF defenses confirm that important actions are intentional.

But the castle still needs good architecture. Sensitive rooms should be separated. The database should not be directly exposed. Administrative functions need stronger controls. Logs should record meaningful events. Dependencies should be updated. Secrets should be protected. Backups and incident response should exist before a crisis happens.

The biggest lesson is that web security is not one feature. It is a collection of engineering decisions made across the entire application lifecycle. A secure application assumes users can manipulate the client, treats external input as untrusted, checks authorization on the server, protects sessions, separates data from code, and continuously monitors for unexpected behavior.
